> **本篇导读**

## 1. 概念底座:RAG 工程最难的不是做出来,而是知道自己错了

任何 RAG 系统都由"解析→切块→索引→检索→生成→评估"这几环组成,每一环怎么搭,网上教程遍地都是。真正的分水岭是一个特别朴素的问题:**你怎么知道它是对的?**

RAG 的失败有一个共同形态:**静默**。检索错了照样返回结果,生成编了照样带引用,权限漏了照样 200,评估管道坏了照样打出一个像模像样的分数。传统软件的失败是崩溃和报错,RAG 的失败是"看起来在正常工作"。所以这套方法论只能围着两件事转:把失败逼得响一点,再验证你的验证本身没坏。

业界的应对手段是一个光谱:

| 手段 | 解决什么 | 解决不了什么 |
|---|---|---|
| 单元测试 / CI | 代码逻辑回归 | 语义正确性("答案对不对") |
| golden set + 程序化指标 | 检索召回、引用命中可量化 | 答案质量、忠实度 |
| LLM-as-judge | 忠实度/正确性可批量评 | 裁判自己也会错、也会被管道 bug 污染 |
| 对抗审查(red-team) | 挖"没人想到要测"的路径 | 成本高;结论也可能误报 |
| 可观测性 | 线上失败可定位 | 事前预防 |

没有哪一层能独自兜底。Pharos 的方法论要回答两件事:这几层怎么搭在一起,以及每一层自己坏掉的时候,谁来抓它。

## 2. Pharos 怎么做:四条方法论主线

### 2.1 测试集驱动:考卷先行,而且考卷本身也要被审

Pharos 的所有产品级决策都要过一张考卷:88 题 gold set(72 散文 + 16 表格数值题),五指标(检索召回/MRR/引用命中 + 裁判判忠实度/正确性)。三个关键机制:

- **考卷跑的就是生产代码。** smart-ask 的判定信号(数值题识别/拒答识别/补检腿参数)沉淀在 [src/generator/signals.py:20](../../src/generator/signals.py#L20),生产的 smart-ask 与 eval 的 `--smart-tables` 共用同一模块——"评估的策略"与"上线的策略"从代码层面不可能漂移。
- **数字必须能机械复现。** [eval/aggregate.py:71](../../eval/aggregate.py#L71) 对 results 与判分记录做 sha1 指纹校验,"results 重跑了但没重判"会直接 `SystemExit` 拒绝出数;双层归因只在两模式公共判过的题集上做 paired 差(分母相同才可减)。
- **噪声粒度决定比较方式。** 单轮 LLM 评估底噪 ±2 题,任何横向比较必须配对归因——[eval/run_eval.py:193](../../eval/run_eval.py#L193) 给每行结果打 `retried`/`retry_kept` 标记,就是为了能精确回答"这次改动动了哪几题、没动哪几题"。

**案例:smart-ask 的四轮 88 题裁决。** 用户默认参数问"Netflix 2011-2015 每年净利润"只得到三年,直觉方案是"数值题预置一条 kind=table 检索腿"。四轮实验的结果链:①前置腿把表格题 0.625→0.875,但散文题 0.861→0.792(腿带进的相近数值误伤 5 道原本答对的题)——否决;②失败驱动 + rerank_top_n=30,指标好看但旗舰案例仍失败,诊断出五年表在粗排 31-50 名、精排池装不进——假象;③top_n=50 + 无条件采用重试,忠实度 0.977→0.932(部分回答夹带"未提供 X"的错误缺失声明,X 其实就在 context 里)——否决;④终版:失败驱动 + 只采用完整答出的重试。这段裁决史直接刻在 [src/generator/signals.py:20-25](../../src/generator/signals.py#L20) 的注释里。

**案例:考卷自己也偏科。** 表格检索文本增强落地后,72 题回归只显示成本(3 题 gold 位移、召回 −2.1pp),收益一栏是 0。原因很简单:当年 gen_gold 显式跳过了表格块,考卷全是散文,增强真正管用的题型根本不在卷子上。逐题诊断确认这 3 题位移都是冗余 gold 被挤掉、答案照样答对,才补进 16 道过了程序化 QC 的表格题,72→88 宣布口径断代。教训:**改动的验收标尺必须覆盖改动的受益题型,否则 eval 会系统性地反对一个正确的改动。**

### 2.2 诊断→修复→验证:失败是待诊断的 bug,不是 verdict

项目全程执行一条纪律:任何"测试失败/行为异常/方案跑不通",禁止直接下"X 不行"的结论,必须走完 诊断(≥多个候选根因)→修复(能解释为什么有效)→验证(复现原 bug 的命令 + 修后同命令的实测对比)。

**案例:vLLM 探针三次"失败",三次 verdict 都是错的。** 跑 vLLM 等价性探针连续三次失败,每次表面结论都是"vLLM 不支持 Qwen3-VL pooling"。逐个挖真根因:①`CUDA_VISIBLE_DEVICES` 给了 GPU-UUID(vLLM 只吃整数索引);②模型 `max_position_embeddings=262144` 让 vLLM 预留 36GB KV cache 直接 OOM(embedding 单次前向根本不需要,加 `max_model_len=8192` 即解);③自己的 `grep -v` 把真实的 EngineCore Traceback 过滤掉了,差点凭空白输出误判"架构不支持"。三个全是配置和工具用法的错,没一个是架构问题——vLLM 明明能加载:G1 min cosine 0.99956,G2 用 88 题真库判下来 top-1 有 98.9% 一致。这条教训直接固化进了探针脚本本身:[scripts/vllm_equiv_probe.py:113-115](../../scripts/vllm_equiv_probe.py#L113) 初始化失败时原样打出真实报错,还注明"未必是架构不支持"。

**案例:BGE-M3 假死的教科书诊断链。** sparse 选型建索引时进程反复假死。诊断路径每一步都有可观测证据:`nvidia-smi` + `ps -o time` 多次采样确认是 blocked 不是在算 → `/proc/<pid>/wchan` 定位到 pipe_write → 进程树发现 defunct 僵尸 → 日志里 dense 进度条出现了两次 = 脚本被跑了两遍。根因:BGE-M3 检测到双 GPU 自动起 multiprocessing pool,spawn 子进程 re-import 无 `__main__` 保护的脚本导致整脚本重跑 + 嵌套 spawn,多子进程争抢 stdout 管道卡死。修复(`main()` + `__main__` 保护、锁单卡)后评估顺利产出选型数据。

**"已修"的标准是两件证据。** 修 bf16 归一化偏差时,不仅改了代码([src/embedder/dense.py:71](../../src/embedder/dense.py#L71) 先 `.float()` 再截维 normalize),还写了"删掉修复就变红"的纯 CPU 守护测试:bf16 张量直接进 `_mrl` 断言 norm=1.0,并反向守卫"bf16 上 normalize 确实会偏 >5e-4"——证明测试测的是真命题。此前第一版 GPU 等价测试被对抗审查判定为**假绿**(它拿到的已经是 fp32,删掉修复也不红),诚实作废重写。

### 2.3 对抗封板:每次"完成"都先派人来反驳

每个阶段的节奏是固定的:**实现 → 对抗审查 → 修 confirmed → 真跑验证 → 提交**。对抗审查不是普通 code review:审查者的任务首先是**试图反驳**发现(常见误报:别处有兜底/触发不可达/文档已声明的取舍),活下来的才叫 confirmed。审查有专门的"镜头",最锋利的一个是——**文档声称已修 ≠ 代码真做了**(留档见 [../methodology/REVIEW_PLAN.md](../methodology/REVIEW_PLAN.md) 与 [../SCALE_OUT.md](../SCALE_OUT.md))。

**案例:评估管道自己被审出大 bug(R5.H1)。** 权威运行报"忠实度 0.83、17% 论断无据",被当成开放问题,甚至据此收紧过 grounding prompt(实测反噬 −0.12 后回退)。R5 把 eval 方法论自身当靶子:发现裁判输入被 `CTX_CAP=5000` 头截断,而 ctx_text 中位 16k——**裁判只看到约 40% 的 context**,16 个 unfaithful 判定里 12 个是"被引证据恰好被截掉"。去截断后全量 216 个判定单元(72 题 × 3 模式)重判:真实忠实度 ≈1.0。所谓 17% 幻觉几乎全是测量伪影,之前的 prompt 收紧是在修一个不存在的问题。现在 [eval/dump_judge_units.py:21](../../eval/dump_judge_units.py#L21) 的 `CTX_CAP=200000` 注释就是这条教训的墓志铭。

**案例:防御纵深会掩盖内层回归(R5.M2)。** ACL 有两道闸:Qdrant prefetch 级硬过滤下推 + 出口 `acl_admits` 复核。只要出口闸在,下推层回归了测试照样全绿。修法是在回归测试里**故意关掉外层**:[eval/acl_regression.py:123-138](../../eval/acl_regression.py#L123) 把 `acl_admits` monkeypatch 成恒 True,重跑 5 身份 × 4 文档的泄漏矩阵,要求仍然 0 泄漏——证明第一道防线本身有效,而不是被兜底掩盖。

**案例:异常继承树上的断链(阶段 F 审查)。** 文档声称"docker kill 副本时客户端无感重试",审查按"真实故障注入会产生什么异常类型"倒推:docker kill 的典型断连是 `RemoteProtocolError` 和 `ReadError`,而旧代码只捕 `ConnectError + TimeoutException`——链条实际是断的。修为捕共同父类 [src/embedder/remote.py:92](../../src/embedder/remote.py#L92) `httpx.TransportError`(不含 HTTPStatusError,4xx 仍立即冒泡),配两条守护测试([tests/engine/test_remote.py:290](../../tests/engine/test_remote.py#L290)),再真跑:3 副本 + nginx,kill 一个副本期间 50/50 请求全 200。

### 2.4 每个决策有实测背书,每个结论带诚实 caveat

- **数据背书的决策**:sparse 选 BM25 是两类查询实测(精确词 BM25 0.738 完胜 BGE-M3 0.584,整体打平但 BM25 零模型零 GPU);rerank 默认关是因为 +16G 显存、每查询数秒,但数据(MRR 0.566→0.867,+53%)留着给需要的人开;RRF 权重扫描峰值只比等权高 0.04 且依赖查询分布——**实测后拒绝优化**也是一种被数据背书的决策。
- **诚实 caveat 的结论**:"E1 逐元素等价 + Qdrant 确定性 ⇒ top-k 一致"的推理被审查驳倒(HNSW 近似 + RRF 名次融合会放大微差),于是从"逻辑保证"降级为"未验证缺口"写进文档;agentic 编排在本 workload 上净负(Δ−0.097,n=72 paired;幅度受 eval#0 组装偏置影响、待修复后复跑,方向大概率成立)照样发布;[../SCALE_OUT.md](../SCALE_OUT.md) 里留着一段自我供词——"我曾宣称透传三出口,实际一个出口都没改,被自己的核实纪律逮住"。错误记录不删,本身就是方法论的展品。

## 3. 为什么这么设计:四种"更省事"的做法是怎么被否决的

**备选 A:靠单测 + CI 就够了。** 被三次同型翻车否决——全是"自己给自己打分"的指标假绿:orphan=0 只量 adapter↔chunker 一致性,对"提取前就丢的内容"全盲(docx 文本框整整丢 390 段仍报零丢失);xlsx 单元格覆盖 100% 掩盖 ~33% 的区表头是标题行(列名↔数值绑定这个核心卖点已坏,指标量不到);覆盖率提取器自己漏读 list_items,把 MinerU 判低 8 个百分点差点选错主力 parser。三次的共同解法:**独立 ground-truth + 对抗测量**,这成了默认流程。

**备选 B:跑一次大评估 + 人工抽查定案。** 否决理由是噪声:±2 题的底噪意味着"这轮 0.83、上轮 0.81"不构成结论。必须配对归因(逐题 diff,区分"改动触发面"与"未触发面的噪声翻转"),而配对要求 results 与判分严格对齐——这就是 aggregate 指纹闸门的由来。

**备选 C:评审结论是权威,修完就翻篇。** 否决:R3 时代坐实的"17% 引用张冠李戴是 LLM 行为",到 R5 才查清主要是裁判管道的截断伪影。**评审结论也要接受再评审**,否则第一次误诊就变成永久档案。

**备选 D:confirmed 的问题全部立即修。** 否决,而且这条否决最能体现工程判断——切块类改动会让 chunk id 平移(本仓实测过一次教训:表格信号增强时面包屑把 23 个空占位表格"救活",全库 7652→7675,同文档后续 chunk id 全部平移、旧 gold 集体错位,当场加存在性门控回滚);检索/生成交付内容的改动会使已发布的评估数字失真。所以 confirmed 要分流:行为无关的健壮性修复立即落地,改变输出内容或需要 GPU/compose 环境验证的延期并留修法草图(详见 §4.2)。

### 4.2 延期的:"确认了但不能马上改"本身是工程判断

这些问题**全部被对抗验证 confirmed**,修法草图都写好了,但按纪律延期——理解"为什么不马上修"比"修了什么"更有教学价值:

- **CJK 无空格文本切不动**(chunker#1):[src/chunker/core.py:197](../../src/chunker/core.py#L197) 的切分正则要求句末标点后有空白,中文句号后没有空格 → 3200 字中文段在 max=900 预算下仍产出单个 1882 token 的 chunk,预算契约失效。**延期原因:改切块边界 = 同文档 chunk 数变化 = chunk id 平移 = 旧索引必须重建 + eval 重跑。** 修法草图(全角标点零宽切分双分支)已备,等一个"本来就要重建索引"的窗口一并落地。§8 的实验二可以亲手复现它。
- **eval 的 agentic/decompose 模式 context 组装绕过生产 Generator**(eval#0):少装了两个已上线的修复(表格 content_raw 补回、section_path 面包屑),对 agentic 系统性不利——**这条直接动摇"agentic 净负 Δ−0.097"的幅度**(方向大概率仍成立:历史 72 题全散文时影响小,但 88 题口径下需复跑)。延期原因:修完三路对比数字会变,必须重跑评估后统一更新结论,不能只改代码不改数字。在此之前,所有引用该 Δ 的地方都要带这个 caveat。
- **nginx 读超时(130s)与客户端最坏重试链(~361s)脱节**(deploy#0):inference 前向 hang 时客户端 130s 拿 504,pharos 工作线程却继续重试满 ~361s 烧线程。延期原因:修法(重试加壁钟总 deadline + 两端预算等式互相引用)需要 WSL compose 环境注入故障实测,不是纯代码改动能验证的。
- **表格 gold 的 QC 闸门只防"编造数"不防"错配数"**(eval#2):16 题小样本下 1-2 条错 gold 就是 6-12 个百分点。延期原因:只影响未来的 gold 重新生成,且重生成会再次口径断代——**审计现有 gold 优先于重生成**。
- **索引期逐 chunk 编码无批处理**(embedder#3):修法本身简单,但本仓自己立过等价性标准(bf16 偏差 1.002 都要修),批前向 vs 单条前向在 padding 下有数值差异风险,**需 GPU 实测批/单编码 cosine 等价后才可合入**——否则新建库与既有库产生系统性微偏。

### 4.3 refuted 与结论冲突:对抗验证不是橡皮图章

35 条疑似问题里,1 条被干净地反驳(readyz 绕过 Store._lock——嵌入式模式下 serve 进程零写路径,"读读安全"是仓库自声明的并发模型,卫生加固留档为可选);1 条两轮验证结论冲突(create_app 写进程级 env,生产入口一进程一 app 触发不可达,保守留档)。**能产出 refuted 的验证流程才可信**——如果对抗验证从不反驳,它就退化成了确认偏误的橡皮图章。

## 5. STAR 故事集:12 个真实故事,按行为面问题归类

> 用法:每个故事压缩成 S/T/A/R 四拍 + 一句可迁移的方法论。面试时按需展开,数据点务必带口径(72 题和 88 题不可混)。

### 5.1 "讲一个你排查过的最难的 bug"

**① BGE-M3 多进程 re-entry 假死**
- **S**:sparse 选型评估建索引,进程反复假死:GPU util 0%、CPU 时间不涨,重跑还见 exit 9 和 freeze_support 报错。
- **T**:不换方案不盲目重跑,找出真根因让评估跑完。
- **A**:采样排除"在计算"→ `/proc/<pid>/wchan` 定位 pipe_write → 进程树见僵尸 → 日志里 dense 进度条出现两次=脚本被跑了两遍。根因:库检测到双 GPU 自动起 multiprocessing,spawn 子进程 re-import 无 `__main__` 保护的脚本;多子进程争抢 stdout 管道(`| grep | tail` 不消费)卡死。
- **R**:`main()` + `__main__` 保护 + 锁单卡,评估产出选型数据(BM25 0.738 vs BGE-M3 0.584)。
- **迁移点**:诊断链每一步都要有可观测证据;"假死"先区分 blocked 与 computing。

**② 探针三连坑:健康检查自己成了故障源**
- **S**:上多副本前审查发现 /readyz /healthz 是 sync def,与 GPU 前向、最坏 ~361s 的检索共享 40 线程池。
- **T**:高负载时探针排队饥饿 → 编排把**正常干活的副本**全摘掉 = 全局 outage,负载越高就绪信号越假。
- **A**:把探针改成 async(纯内存读直接跑在事件循环上),qdrant 探活 offload 到专用 8 线程 limiter([src/pharos/service.py:40](../../src/pharos/service.py#L40)),inference 探活显式 Timeout(1.5s)——审查还抓到默认 3s 各阶段累计最坏 ~9s,超过 healthcheck 5s 预算,探针自己就会误判。落地后实测又抓到第三例:nginx 容器内 `localhost` 先解析到 ::1 被拒 → 纯粹是探针假阳,钉死 127.0.0.1。
- **R**:3 副本 + nginx,kill 一副本期间 50/50 请求全 200。
- **迁移点**:探针的资源路径、超时预算、名字解析都必须与业务隔离并显式钉死;"负载越高信号越假"是探针设计的死罪。

**③ docker kill "无感"承诺断在异常继承树上**
- **S**:文档声称 kill 副本客户端无感,审查按"kill 实际产生什么异常"倒推:典型断连是 RemoteProtocolError/ReadError,旧代码只捕 ConnectError+Timeout。
- **T**:两个类型绕过重试被吞成无重试的通用错误,链条实际是断的。
- **A**:改捕共同父类 `httpx.TransportError`(不误吞 4xx),503 硬编码放宽到 ≥500(nginx/K8s 对被 kill 后端返 502/504);两条守护测试常驻 CI。
- **R**:端到端实测 50/50 全 200。
- **迁移点**:failover 是"nginx 重试 × 客户端异常谱 × 优雅停机"的端到端链条,任何一环的类型系统细节都能让整体承诺失效。

**⑤ 66.6ms 杀死自己的懒加载设计**

### 5.3 "讲一个跨层 / 跨组件的 bug"

**⑦ N7 唯一一次"自信错答":双根因横跨检索与生成**
- **S**:问 Netflix 总营收,系统把分部营收当总营收答出,带真实引用——比拒答危险得多。
- **T**:诊断出**双根因**:检索侧,表格块可检索文本只有 caption,列头/行标签锁在 content_raw 不参与 embed,数字题的表格块被散文挤出 top-k;生成侧,范围证据(小节路径)根本不进 prompt,表格正文无一字"分部",模型无从判断。
- **A**:chunker 加表头+行标签检索信号(数据单元格刻意不进——数字无检索语义);generator 把 section_path 并入 source 行 + 窄靶数值范围约束。关键实验:只加约束不给证据,实测无效——**约束没有证据就是空文**。重建索引时还当场抓到副作用:面包屑把 23 个空占位表格救活,全库 7652→7675、chunk id 全体平移,加存在性门控恢复。
- **R**:72 题回归忠实度 0.972→1.000、正确性 0.847 持平;动机案例中文问法直接答对。
- **迁移点**:跨层 bug 的修复要在每一层各自闭环,还要盯住修复自身的二阶副作用。

**⑧ 修可用性的补丁制造更大的可用性事故:锁下沉**
- **S**:为吸收推理服务预热加了重试退避,对抗审查发现退避 sleep 发生在检索大锁内——服务不可用期间每个查询满额退避持锁,**整副本所有查询串行停摆**。
- **T**:并发复现:第二个查询 2.90s(完全串行)。
- **A**:不挪 sleep 打补丁,而是定性"一把大锁裹着三件本质不同的事",锁下沉到资源:Store._lock / GPU _fwd_lock(Remote override 成 nullcontext)/ _load_lock(single-flight)/ _cache_lock(双段,encode 在锁外);并接受"两线程同 query 同时 miss 各算一次"的良性竞态。测试还诚实删掉一个假绿(GIL 下单 dict 操作原子,删锁也不 corrupt)。
- **R**:2.90s→1.77s 真并发;9 项并发测试用"删锁必红"反证自身灵敏度。
- **迁移点**:锁的粒度必须匹配资源而非代码段;修复的排期本身是风险决策(此修没有塞进当期,而是排到"真起 remote 前必修")。

**⑨ "生产闭合、检索敞开":small-to-big 跨 ACL 泄漏**
- **S**:两条 chunk 生产路径都 fail-closed 了,安全审计仍确认 8 处真泄漏。
- **T**:small-to-big 在向量库硬过滤**之后**按 idx 范围从原始 elements 重新取材——命中一个公开小节,会把同区间内被收紧的兄弟小节明文捞进 big.text。旧铁律"big-block 只在同文档内取材故不越权"是错误声明:**同文档 ≠ 同 ACL**。
- **A**:acl_index(element idx→chunk acl,冲突取更严)+ admits 等价类门控(未知 idx fail-closed),出口二次校验;顺手把"deny 字段静默不生效"从 schema 里删掉并显式警告——静默不生效的安全字段是最毒的契约失败。
- **R**:真语料 3/79 个 big-block 泄漏 → 0/79,且 78/79 仍正常长大(安全没有牺牲召回);"legacy 路径必泄漏"做成契约锁测试。
- **迁移点**:权限过滤之后的任何"再取材"路径都是旁路候选;安全修复要证明没有以召回为代价。

### 5.4 "你怎么知道你的评估是对的?"(评估自身被污染)

**⑩ 忠实度 0.83 → ≈1.0:量尺坏了,不是系统坏了**
- **S**:权威评估报忠实度 0.83,"17% 幻觉"进了文档,还驱动过一轮 prompt 收紧(反噬 −0.12 回退)。

**⑪ orphan=0 三连坑:自指标的自欺**
- **S**:office 扩展首跑报 orphan=0(内容零丢失),自信满满。

### 5.5 "讲一次你说服别人 / 被说服的经历"

## 7. 追问预演

**Q1:88 题太少了,你的结论可信吗?**
思路:承认小样本,展示对策。①噪声量化过:±2 题底噪,所以从不比较裸聚合分,一律配对归因(retried/retry_kept 标记内建在 run_eval 里);②口径纪律:72→88 宣布断代,新旧数字禁止直接对比;③分层报告:表格 16 题单独拆分统计;④16 题小样本的风险自己文档里写着(1-2 条错 gold 就是 6-12 个百分点,eval#2 确认了 QC 闸门防编造不防错配,列入延期修复)。关键词:配对归因、口径断代、已知盲区清单。

**Q2:LLM-as-judge 本身不可靠,你怎么办?**
思路:①去偏三角——gold 与裁判用异厂前沿模型,被测系统用 DeepSeek,GEN_MODEL 默认回退生产配置("测的就是部署配置"是代码默认值不是口号);②拒答双向计分——合理拒答算忠实但算错,两个指标方向相反互相制衡,全拒刷不了忠实度、瞎编刷不了正确性;③裁判输入=生成器输入的逐字节原文(R5.H1 的教训);④双裁判 AND 复核,与单裁判一致性有实测(agentic 0.764→0.750 略严)。

**Q3:对抗审查和普通 code review 有什么区别?**
思路:三点。①任务是**反驳**不是确认:每条发现先派独立验证员找误报(别处有兜底/触发不可达/已声明取舍),35 条里 1 条被干净 refuted、1 条两轮冲突保守留档——能产出 refuted 的流程才可信;②有镜头:"文档声称已修 ≠ 代码真做了"、"守护测试在 CI 上真的会跑吗"(有个 fail-loud 守护曾被 GPU skipif 吞掉,CI 上删掉被保护代码也不红);③confirmed 分流而非全修:改变输出内容的延期并留草图,因为 chunk id 平移和评估口径失真的代价实测踩过。

**Q4:怎么防止"为了过测试而写测试"?**
思路:测试要能反证自身灵敏度。①"删修复即红":bf16 守护测试特意构造 bf16 张量直接进 `_mrl`,还反向守卫"不修的话偏差确实 >5e-4";②"关外层证内层":ACL 回归 monkeypatch 掉出口复核,证明 prefetch 下推本身挡住越权;③诚实删假绿:有个 cache-corruption 测试在 GIL 下删锁也不 corrupt,承认它测不到真命题,删掉。

**Q5:这套方法论成本很高,值吗?怎么取舍?**
思路:①分流就是成本控制:本轮 34 confirmed(2 条跨层重复,去重 32)只立即修 17 项行为无关的,其余 15 项延期到"本来就要重建索引/重跑评估"的窗口合并摊销;②severity ≠ occurrence:打穿核心卖点的低频缺陷必修(xlsx 表头污染 ~33% 区受影响),不打穿的高频容忍(est_tokens 启发式验证后不改——误差两个方向都有兜底);③有实测后拒绝优化的先例:RRF 权重扫描峰值只比等权高 0.04,不值客户端融合复杂度。

**Q6:你发布了 agentic 净负的结论,后来发现评测对它不利,怎么处理?**
思路:诚实分两步。①方向与幅度分开:eval#0 确认 agentic/decompose 的 context 组装少装了两个生产修复(表格 content_raw 补回、面包屑),**幅度存疑**;历史 72 题全散文时影响小,方向大概率仍成立;②修复已 confirmed 但延期——因为修完三路对比数字会变,必须重跑后统一更新,在那之前所有引用 Δ−0.097 的地方带 caveat。这恰好演示"结论也要接受再评审"。

**Q7:指标和手工体验矛盾时信谁?**
思路:都不无条件信,冲突本身是诊断信号。smart-ask 第二轮:指标好看但旗舰手工案例失效,深挖出"精排池深度 < 对的块的粗排名次"(top_n=30 装不进 31-50 名的五年表)——指标掩盖了一个结构性问题。反过来,前置腿让旗舰案例变好但配对归因暴露误伤。规则:旗舰案例是"存在性证据",配对归因是"总量证据",二者必须同时过。

**Q8:如果只能带走一条方法论?**
思路:"独立 ground-truth + 对抗测量"。三次翻车(orphan=0、xlsx 100% 覆盖、覆盖率提取器自坑)全是同一型:用系统自己的输出给自己打分。凡指标不锚定系统外真值,它量的就是一致性而不是正确性——评估管道截断案(0.83→1.0)本质也是这一型:裁判看到的不是系统真实看到的。

### 实验二(纯 CPU):亲手复现一个"confirmed 但延期"的真 bug

§4.2 的 chunker#1(CJK 无空格文本切不动)可以两分钟复现(Git Bash;若未 `pip install -e .` 则前缀 `PYTHONPATH=src`):

```bash
cd <仓库根>
PYTHONPATH=src python - <<'PY'
from chunker.core import _sentence_split, est_tokens
zh = "模型在长上下文里的检索退化是一个已知问题。" * 150   # 无空格中文,约 3000 字
pieces = _sentence_split(zh, hi=900, lang="zh")
print("无空格中文:", len(pieces), "片; 最大片 est_tokens =", max(int(est_tokens(p,"zh")) for p in pieces))
en = zh.replace("。", "。 ")                              # 句号后人工加空格的对照组
pieces2 = _sentence_split(en, hi=900, lang="zh")
print("加空格对照:", len(pieces2), "片; 最大片 est_tokens =", max(int(est_tokens(p,"zh")) for p in pieces2))
PY
```

实测输出:无空格中文 **1 片、1852 token**(预算 max=900 被击穿);对照组 3 片、每片 ≤892。然后思考两个问题:①为什么 [src/chunker/core.py:197](../../src/chunker/core.py#L197) 的正则 `(?<=[。！？.!?])\s+` 对中文失效?②这个 bug 已被 confirmed、修法草图都有(全角标点零宽切分双分支),为什么不当场修?(提示:修后同文档 chunk 数变化 → chunk id 平移 → 旧索引与 gold 全部错位——回看 §3-D 的 7652→7675 教训。)能把第②问讲清楚,就理解了本篇的核心:**修复的时机也是工程决策。**

## 9. 诚实边界

面试中主动承认这些,比被追问出来体面得多:

1. **考卷小且有已知缺陷。** 88 题(表格仅 16 题),错配型错 gold 可以穿过现有 QC 闸门(eval#2,confirmed 未修);表格题采样有字典序偏斜风险(eval#3)。话术:"我的结论都在这张考卷的信度范围内陈述,考卷自身的缺陷清单是审查产物的一部分。"
2. **agentic 净负的幅度存疑。** eval 的 agentic/decompose context 组装少装了两个生产修复,对它们系统性不利(eval#0 confirmed);方向大概率成立,幅度要等复跑。引用 Δ−0.097 时必须带此 caveat。
3. **对抗审查是 LLM 辅助 + 人工裁决,不是形式化验证。** 有过两轮验证结论冲突的条目(create_app 写 env),按保守处理留档;confirmed 也可能错,所以延期项都留了修法草图供再验。
4. **部分承诺只在实测过的形态下成立。** "docker kill 无感"实测的是 3 副本 + nginx 的 compose 形态;inference 前向 hang 的健康盲区(deploy#6)、nginx 超时预算脱节(deploy#0)都 confirmed 未修——单卡前向串行 ~3.2 req/s 的吞吐上限,多副本也没能抬高(多副本扩的是非 GPU 并发和崩溃隔离,不是 QPS)。
5. **方法论有幸存者偏差。** 本篇讲的都是"抓到了"的故事;没被任何一轮审查抓到的问题,按定义不在这份文档里。守护测试和对抗镜头降低的是概率,不是把它降到零。

## 10. 尾声:这套文档的诞生,本身就是这套方法论的一次实践

最后一个故事的主角是你正在读的这套文档。

写作前,六个子系统(chunker/embedder/generator/service/eval/deploy)各派一个分析师并行深读,产出知识地图的同时收集了 **35 条"疑似设计问题"**。每一条立即派独立的对抗验证员**先试图反驳**——按本篇 §2.3 的同款纪律,常见误报(别处有兜底/触发不可达/文档已声明的取舍)先筛一遍。结果:**34 条 confirmed、1 条干净 refuted;34 confirmed 里 2 条是跨层重复报告(deploy 复审重报 embedder/service 各一条,已随修),去重后 32 个不同问题**。

去重后的 32 个不同问题按 §3-D 的分流纪律处理:**17 项行为无关的健壮性修复直接落地**(§4.1),**15 项凡改变切块/检索/生成输出内容或需 GPU/compose 环境验证的延期**(§4.2)——因为切块改动会 chunk id 平移(7652→7675 的教训就在眼前),检索交付内容的改动会使已发布的评估数字失真。验证证据齐全:修复前 `pytest tests -q` = 224 passed / 4 skipped,修复后 = 259 passed / 5 skipped(新增 36 用例;唯一新增 skip 是 server-gated 测试,临时起真 Qdrant server 实测 264 passed / 0 skipped)。

过程里还有一个插曲:首轮对抗验证的 19 个 agent 因会话限额集体失败,限额重置后断点续跑——已完成的 22 个从回放缓存恢复,全部跑完。**评估与验证的基建,自己也要有可恢复性**——这句话在 eval 的指纹闸门里出现过一次,在这里又出现了一次。

所以这套文档不是"写了一份关于方法论的说明书",而是方法论又完整地自转了一圈:深读 → 疑似 → 对抗验证 → confirmed 分流 → 修复带双证据 → 延期带修法草图 → 把过程本身写成教材。如果面试官问"你说的这套流程,最近一次用是什么时候"——答案是:**用它生产了你现在看到的这份答案。**
